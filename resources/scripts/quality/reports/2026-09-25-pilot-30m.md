## OOM recovery check

Inspection found that an uncaught OOM can terminate the daemon Redis worker while
HTTP threads keep the JVM alive. Docker does not restart a process that is still
running. A disposable container reproduced that failure mode with a 16 MiB heap:

| Configuration | Worker stops after OOM | JVM remains alive after worker stops | Exit code |
|---|---|---|---:|
| Without ExitOnOutOfMemoryError | yes | yes; probe prints an alive marker | 0 after the probe ends |
| With ExitOnOutOfMemoryError | JVM terminates | no | 3 |

The production candidate image was used with networking disabled and a 128 MiB
container limit for these fault-injection tests. Production recordings were not
used for fault injection. The pilot's existing Docker restart policy is
`unless-stopped`, which can recover the process once the JVM exits.

## Deployment and monitoring correction

After the successful initial observation, the pilot was recreated with
`JDK_JAVA_OPTIONS=-Xmx3584m -XX:+ExitOnOutOfMemoryError`. The JAR was unchanged.

startup as an OOM. Its automatic rollback restored the baseline image. There was
no actual production OOM: the container was healthy, restart count was zero, and
the log contained no genuine OOM exception.

The substring detector was replaced with `monitor_errors.count_java_oom`, which
recognizes standalone exception names and excludes embedded JVM option names.
